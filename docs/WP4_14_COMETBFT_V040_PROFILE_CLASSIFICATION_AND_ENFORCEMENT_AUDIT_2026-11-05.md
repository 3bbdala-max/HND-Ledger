# HND v0.2 — CometBFT v0.40.0 profile classification and enforcement audit

**Date:** 2026-11-05  
**Branch:** `phase-0.2-planning`  
**Reviewed baseline:** `9ebda4b9d0bed17351f7d3de3f47af33ed98060d`  
**Status:** Static source review and design classification only. No source, test, or workflow files changed. No tests or network processes executed.

## 1. Executive conclusion

The existing CometBFT smoke harness is a useful local integration test, but it does not freeze or verify a complete network profile.

The four-validator script:
- initializes four temporary homes using the supplied CometBFT binary;
- creates one validator set and one common Genesis document;
- copies the same Genesis bytes to all four homes;
- edits a selected set of listener and peer-routing keys in each `config.toml`;
- leaves the remainder of each generated configuration at the binary's `init` defaults;
- launches all four nodes without a complete resolved-profile comparison.

The Genesis validator helper parses the document using CometBFT's Go types and checks that there are four validators. It does not assert an approved consensus-parameter set, a pinned CometBFT profile digest, or equality of the resolved node configurations.

**Disposition:** no release-grade CometBFT profile enforcement exists in the reviewed scripts. Keep production/network launch blocked until a version-specific profile and pre-start verifier exist.

## 2. Important distinction: consensus validity vs liveness vs local operation

A profile should not indiscriminately hash every TOML key into one "consensus config". Doing so would make local ports and paths look like network consensus identity and create false mismatches. Conversely, treating all TOML values as harmless local settings would omit parameters that affect block validity or consensus execution.

Use three independently versioned sections.

### A. Consensus-state parameters — must be identical and authenticated

These are parameters committed in the CometBFT Genesis/consensus-parameter state or otherwise define the rules by which a block/evidence item is accepted. For the pinned CometBFT v0.40.0 schema, explicitly enumerate and validate at least:

- block maximum bytes;
- block maximum gas;
- evidence maximum age in blocks;
- evidence maximum age duration;
- evidence maximum bytes;
- validator public-key type and validator-set records;
- validator voting power and total voting power;
- initial height and chain ID;
- consensus/application protocol versions where represented in the versioned Genesis or protocol contract.

The exact schema must be extracted from the pinned v0.40.0 Go types and source, not guessed from a newer CometBFT release. The current helper's successful parse is only a schema parse; it does not compare these fields with an approved value.

### B. Consensus timing and node behavior — standardize and constrain, but classify accurately

Examples include:
- propose, prevote, precommit, and commit timeouts and their deltas;
- empty-block creation and interval;
- consensus WAL and replay behavior;
- mempool admission, recheck, size, and broadcast policy;
- P2P peer limits and gossip behavior.

These settings can affect liveness, transaction propagation, operational recovery, or inclusion timing. A difference does not automatically mean two validators apply different deterministic transaction-validity rules. The profile should record and validate them as an approved **operational consensus-service profile**, with explicit allowed ranges and rationale. Do not mislabel every timeout mismatch as a block-validity divergence.

For the exact v0.40.0 binary, derive the full key list and defaults from the generated TOML and the pinned source. The current repository scripts do not contain that complete list.

### C. Node-local deployment settings — must be safe, but must not pollute consensus identity

Examples include:
- RPC listener address/port;
- P2P listener address/port;
- ABCI proxy address/port;
- persistent peer routes and relay endpoints;
- local data and configuration paths;
- log level and local instrumentation endpoints.

These may legitimately differ by validator. They need a separate deployment-policy validator: for example, prevent public RPC exposure where not intended, ensure ABCI binds only to an approved local interface, validate peer identity/address binding, and ensure paths and permissions are safe.

Private validator keys, node keys, remote-signer credentials, and Noise identity private keys are secret material. Never put private bytes or secret-bearing paths into a public consensus profile or attestation.

## 3. What the current repository actually verifies

| Item | Current evidence | Missing enforcement |
|---|---|---|
| Common CometBFT Genesis | Four-validator harness copies the same generated bytes to each temporary home | Production-pinned Genesis digest checked by every node before start |
| Genesis parsing | Go helper uses `types.GenesisDocFromFile` and checks validator count | Assertions for approved chain ID, initial height, consensus params, validator set, and exact profile digest |
| Validator uniqueness | Harness checks unique P2P node IDs and consensus addresses | Authenticated approved validator-set artifact, voting-power policy, activation/rotation controls |
| TOML listeners and peers | Selected keys rewritten in the smoke harness | Full strict parse and classified-key validation |
| Remaining TOML defaults | Inherited from `binary init` | Explicit values or version-pinned default lock; no silent default drift |
| CometBFT executable | Supplied through `--binary`; source tree supplied separately | Runtime version and binary checksum verification before node/signer launch |
| Resolved config identity | Not emitted as a complete attestation | Canonical profile digest and reproducible per-node attestation |
| HND application config | Legacy CLI config path; separate audit documents the `max_amount` gap | Config-v1 digest bound into HND Genesis and durable state |

The four-validator harness proves that its own fixture supplied a shared Genesis and matching values for the explicit HND CLI arguments. It does not prove that a production operator cannot launch one node with a modified TOML setting or a different binary.

## 4. Required profile artifacts

Keep these artifacts separate to preserve clear trust boundaries:

1. **CometBFT consensus-state profile** — exact v0.40.0 consensus parameter schema and approved values.
2. **CometBFT service profile** — approved timeout, mempool, P2P, WAL, and other node-behavior values, each classified with its impact.
3. **Validator-set artifact** — consensus public keys, addresses derived/validated from keys, voting power, activation height, and rotation/governance procedure.
4. **CometBFT Genesis artifact** — exact canonical Genesis bytes, including chain ID, initial height, consensus parameters, validator set, and HND application state.
5. **HND Config-v1 artifact** — deterministic HND application policy; its missing `max_amount` binding is covered by the companion runtime Genesis/config audit.
6. **Node-local deployment profile** — local listeners, peer routes, file paths, service limits, and hardening requirements.
7. **Software identity manifest** — exact CometBFT version, binary SHA-256, source commit/tag, HND source commit, dependency lock identity, and profile schema versions.

Each artifact needs a distinct domain-separated digest. The aggregate network release manifest may reference those digests, but must not collapse secret material or node-local endpoints into the deterministic application state hash.

## 5. Pre-start enforcement sequence

Before a validator process or remote signer is started:

1. Verify the CometBFT binary exists and its reported version matches the approved release.
2. Verify the binary SHA-256 against a digest delivered through an independently trusted channel.
3. Verify the HND software commit/build identity and dependency lock.
4. Strictly parse the exact CometBFT Genesis bytes; reject duplicate JSON keys, malformed values, and unsupported schema.
5. Recompute and compare the pinned Genesis digest.
6. Compare chain ID, initial height, consensus parameters, validator set, voting power, and key types with approved artifacts.
7. Parse the actual resolved `config.toml`; reject duplicate keys, missing required keys, invalid types, and unclassified keys unless explicitly allowed by the schema policy.
8. Compare all consensus-state fields with Genesis and all service-profile fields with approved values/ranges.
9. Validate local endpoint policy separately; allow only intended node-specific differences.
10. Verify validator key identity against the approved validator-set entry without exposing private key material.
11. Verify remote signer identity and anti-double-sign state under the separate signer recovery controls.
12. Emit a redacted, reproducible attestation containing all artifact digests and software identities; only then allow node startup.

A launcher-side check is necessary but not sufficient if operators can bypass it. Production packaging and service supervision must make the verifier the mandatory entry point.

These are proposed tests; none were executed in this review.

| ID | Mutation | Required result |
|---|---|---|
| CMT-PROF01 | Change Genesis block max bytes | Genesis/profile verification rejects |
| CMT-PROF02 | Change Genesis block max gas | Genesis/profile verification rejects |
| CMT-PROF03 | Change evidence age blocks, age duration, or max bytes | Genesis/profile verification rejects |
| CMT-PROF04 | Change chain ID or initial height | Preflight rejects |
| CMT-PROF05 | Change validator key, remove/add validator, or change voting power | Validator-set verification rejects |
| CMT-PROF06 | Change one approved timeout/service-profile value | Service-profile verification rejects or reports explicitly approved deviation; never silently accepts |
| CMT-PROF07 | Change CometBFT binary version but preserve Genesis | Binary identity verification rejects |
| CMT-PROF08 | Change binary bytes while preserving version string | Binary checksum verification rejects |
| CMT-PROF09 | Change local RPC/P2P port only | Consensus digest unchanged; local deployment policy revalidated |
| CMT-PROF10 | Change peer route only | Consensus digest unchanged; peer policy and node-ID binding revalidated |
| CMT-PROF11 | Add unknown or duplicate TOML key | Strict profile parser rejects |
| CMT-PROF12 | Change an inherited default after a binary upgrade | Profile verifier detects drift before launch |
| CMT-PROF13 | Restart validator with same approved artifacts | Attestation digests and validator identity remain stable |
| CMT-PROF14 | Start one of four validators with a different profile digest | That validator fails before joining P2P/consensus |

## 7. Next implementation order

1. Extract the exact CometBFT v0.40.0 Genesis and config schemas from the pinned Go module.
2. Build a machine-readable classification of every generated `config.toml` key: consensus-state, service/liveness, local deployment, or secret reference.
3. Freeze approved values and allowed deviations with explicit rationale.
4. Add canonical vectors for Genesis, consensus-state profile, service profile, validator set, and aggregate release manifest.
5. Implement a strict read-only preflight verifier before changing the node launch scripts.
6. Add negative mutation tests and four-node mismatch startup tests.
7. Only after those pass, make the verifier mandatory in the production service entry point and produce signed deployment attestations.

## 8. Scope and final disposition

This report is based on static inspection of the repository's CometBFT scripts, Genesis validator helper, and previous profile audit. It deliberately does not claim a complete enumeration of every v0.40.0 TOML key because the repository's current scripts inherit most generated defaults and the pinned external source tree is supplied at test runtime rather than stored as a local module in the reviewed tree.

No source, test, or workflow files were modified. No tests or CometBFT network processes were run.

**Final disposition:** the current four-validator local smoke is integration evidence only. It is not a frozen production profile, not a validator admission gate, and not proof of Byzantine safety. Keep production launch blocked pending version-pinned profile extraction, trusted digest verification, and mismatch-test evidence.
