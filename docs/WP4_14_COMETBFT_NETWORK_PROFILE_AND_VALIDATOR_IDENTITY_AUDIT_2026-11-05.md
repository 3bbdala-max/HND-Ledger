# WP4.14 — CometBFT Network Profile and Validator Identity Audit

**Date:** 2026-11-05  
**Branch:** `phase-0.2-planning`  
**Baseline head:** `eb5ab8022204423e288bae5898fa7d1c5d50cf03`  
**Status:** Static source audit only; no source/test changes; no tests run.

## 1. Executive finding

The repository's disposable CometBFT harnesses establish useful validator-key uniqueness and byte-identical Genesis fixtures. They do not yet establish a release-grade, pinned CometBFT network profile. In particular, temporary homes inherit most `config.toml` values from the selected CometBFT binary's `init` defaults, and the harness changes only a selected networking subset.

A shared Genesis file is necessary, but it is not sufficient evidence that every validator runs the same consensus policy.

## 2. Direct source evidence

### 2.1 Four-validator preflight

`scripts/cometbft_v040_four_validator_genesis_preflight.py`:

- Runs the supplied binary's `init --home` separately for four temporary homes.
- Reads each generated `priv_validator_key.json`, checks public-key schema and non-empty identity fields.
- Calls `show-node-id`; checks unique P2P node IDs and unique consensus addresses.
- Constructs four validator records with voting power 10 each.
- Builds one common CometBFT Genesis document, computes SHA-256 over its exact serialized bytes, writes the same bytes to each home, and checks byte identity.
- Validates the Genesis through the pinned CometBFT v0.40.0 Go types.
- Explicitly labels its scope as Genesis-and-identity preflight only; it starts no nodes.

This is valuable fixture validation, not a complete consensus-profile validation.

### 2.2 Four-validator running smoke

`scripts/cometbft_v040_four_validator_network_smoke.py`:

- Initializes each temporary home from the supplied binary.
- Rewrites selected TOML values: `proxy_app`, `abci`, RPC/P2P listeners, persistent peers, PEX, address-book strictness, duplicate-IP behavior, and optional remote signer listener.
- Starts the HND ABCI processes with the same literal `--max-amount` in this test harness.
- Starts the CometBFT nodes and checks convergence/recovery scenarios.

The script does not explicitly set and assert the complete CometBFT consensus parameter set. The common test invocation demonstrates that this harness supplied matching values; it does not provide a production startup guard against one operator changing a consensus setting.

### 2.3 Single-node smoke

`scripts/cometbft_v040_single_node_smoke.py` similarly initializes a temporary home and changes selected ABCI and listener settings. It does not freeze or hash a complete CometBFT consensus profile.

## 3. Configuration domains that must remain distinct

| Domain | Examples | Required identity/control |
|---|---|---|
| HND deterministic application | max amount, amount bounds, transaction count/bytes, transaction format | Config-v1 digest authenticated by HND application Genesis |
| CometBFT consensus | block max bytes/gas, evidence max age/bytes, timeout parameters, validator set and voting power, consensus version | Canonical CometBFT network profile + exact Genesis/profile digest, independently pinned by every validator |
| Operational/networking | RPC and P2P endpoints, local ABCI address, peer routes, log level, worker count | Hardened deployment profile; classify each field and do not accidentally hash local-only values into consensus identity |
| Secret material | validator private key, node private key, signer credentials | Secret/key-management system; never include private material in public profile artifacts |

Do not assume that every field in `config.toml` is consensus-critical. Build and maintain an explicit, version-specific classification against the pinned CometBFT v0.40.0 schema. Conversely, do not omit a parameter merely because it is generated by a default.

## 4. Required profile design

Before a public-network deployment:

1. Pin the exact CometBFT binary version and binary checksum; reject an unexpected version or checksum before node start.
2. Define a versioned CometBFT profile containing every consensus-affecting parameter supported by that pinned version.
3. Define the validator-set artifact separately, including consensus public-key identity, voting power, activation height, and governance/rotation procedure.
4. Canonically serialize the profile and validator-set artifact; define distinct domain-separated digests.
5. Pin the exact CometBFT Genesis bytes/digest and profile digest through a trusted distribution channel. Every validator must verify both before starting.
6. Generate `config.toml` from an explicit deployment template, or parse the resolved configuration and compare all classified values with the approved profile. Do not silently inherit unknown defaults.
7. Fail closed if a required key is missing, duplicated, unknown where strictness is required, or differs from the approved value.
8. Keep local addresses, peer routing, logging and private key paths outside consensus identity unless a specific parameter is proven to affect consensus validity.
9. Record the resolved configuration, binary checksum, Genesis digest, profile digest, validator-set digest, and software commit in a reproducible startup attestation. Do not publish secrets.
10. Add mismatch tests proving that a one-field consensus-profile mutation is rejected before any node or signer starts.

## 5. Minimum validation matrix

- Same binary, profile, Genesis and validator set across all nodes: startup accepted.
- Binary version or checksum mismatch: startup rejected.
- Each consensus parameter changed individually: profile verification rejected.
- Missing/extra validator, changed consensus public key, or changed voting power: validator-set verification rejected.
- Changed local RPC/P2P port only: consensus profile digest remains unchanged, while operational validation still checks safe binding.
- Changed peer route only: consensus profile digest remains unchanged; peer authentication and network policy are independently enforced.
- One validator given a different approved-profile digest: preflight rejects before node launch.
- Restart and recovery preserve the expected validator identity, profile digest, Genesis digest, and application configuration digest.

## 6. Scope and disposition

This report is a static review of the repository scripts and current design documents. It does not claim that a new test was run, that all generated defaults were enumerated, or that a production profile has been approved.

**Disposition:** the existing four-validator smoke remains useful as a disposable integration fixture. It must not be treated as proof of a production-frozen CometBFT consensus configuration. Keep public-network and production gates closed until the version-pinned profile, validator-set governance, startup verification, and mismatch tests are implemented and evidenced.
