# HND-Ledger independent review and ownership-evidence protocol

**Purpose:** Give an independent engineer a repeatable procedure for examining a frozen HND-Ledger candidate, rebuilding it, replaying its tests, and distinguishing technical provenance from legal ownership.

This document is a review procedure, not a certificate, legal opinion, or claim that the project has passed independent review.

## 1. Freeze the candidate

The project owner must identify one immutable candidate commit SHA. The reviewer must record that exact SHA and the repository URL before inspecting code. Do not review a moving branch name as if it were a fixed release.

The reviewer should receive read-only repository access. If the repository is private, access must be granted explicitly by its owner. Do not send passwords, private keys, personal access tokens, or other write credentials to the reviewer.

Record:
- repository URL and visibility;
- candidate commit SHA and tree SHA;
- base commit used for the candidate diff;
- date and time the reviewer obtained the source;
- reviewer identity and declared conflicts of interest.

## 2. Obtain and inspect the source

From a clean environment:

```bash
git clone <repository-url> HND-Ledger
cd HND-Ledger
git checkout --detach <candidate-commit-sha>
git status --porcelain
git rev-parse HEAD
git rev-parse HEAD^{tree}
git log --show-signature --format=fuller -n 20
```

The working tree must be clean, and `HEAD` must equal the recorded candidate SHA. Review the full diff from the recorded base commit, not only the most recent commit.

Inspect at minimum:
- normative protocol documents and canonical byte encodings;
- transaction signature verification and nonce/replay rules;
- genesis construction and supply accounting;
- block header decoding, hashing, state roots, and transaction Merkle roots;
- deterministic block execution and replay verification;
- SQLite transaction boundaries, metadata binding, corruption detection, and recovery behavior;
- dependency declarations, workflow definitions, scripts, and provenance tooling.

## 3. Rebuild and execute the candidate

Use a clean Python environment and record the exact interpreter and dependency versions:

```bash
python --version
python -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip freeze
python -m pytest -q
python -m hnd_ledger.vector_check
python scripts/create_provenance_manifest.py --output evidence/SHA256-MANIFEST.json
python scripts/create_provenance_manifest.py --verify evidence/SHA256-MANIFEST.json
```

On Windows, activate the virtual environment with its platform-specific activation command.

The reviewer must preserve complete command output and exit codes. A green workflow badge is not enough: the workflow must be tied to the exact candidate SHA and expose successful test steps. If GitHub Actions fails before steps or logs are available, report the result as **unobservable job failure**, not as a test failure or test pass.

## 4. Independently test persistence

The current SQLite implementation is a single-host reference store. The reviewer should add or run tests that:
- create a chain from a known genesis allocation;
- append several valid blocks, including multiple transactions from one account;
- close all handles and reopen the database in a fresh process;
- compare replayed balances, nonces, headers, and hashes with the expected values;
- reject a wrong chain ID or changed genesis allocation;
- reject altered headers, block hashes, transaction bytes, row heights, and parent links;
- prove a rejected append leaves no partial block;
- run concurrent append attempts and verify serialization/nonce behavior;
- inject process termination around commit boundaries and test SQLite recovery;
- restore a backup into a separate directory and replay it from genesis.

Do not claim power-loss safety, backup correctness, or disaster recovery until the corresponding fault-injection and restore tests have actually run.

## 5. Verify source integrity and provenance

The SHA-256 manifest identifies a particular Git revision and the contents of tracked files. It is useful for detecting accidental or malicious file changes relative to a trusted copy.

However:
- a manifest generated by the same party who supplies the source is not an independent trust anchor;
- a Git author name/email is self-asserted metadata;
- an unsigned Git commit does not establish who controlled the signing key;
- a hash does not establish when a file existed;
- a public repository does not, by itself, establish legal ownership.

For a stronger provenance record, the release owner should:
1. create an annotated release tag for the frozen commit;
2. sign the tag with a verifiable GPG or SSH signing key;
3. publish the public verification key and its identity-binding evidence through a separate trusted channel;
4. obtain a trusted timestamp for the signed tag or release manifest;
5. retain the original source archive, manifest, test report, and independent reviewer report;
6. record every contributor and the exact contribution they supplied.

A reviewer should verify the tag signature and timestamp independently. Do not accept a screenshot as a substitute for cryptographic verification.

## 6. Establish the legal chain of title

Technical provenance and legal ownership are separate questions. The owner should assemble, outside the source repository where appropriate:
- a dated statement identifying the claimed author and rights holder;
- contributor agreements, copyright assignments, employment agreements, or valid open-source license grants for every contribution;
- a list of third-party libraries, copied code, specifications, and other incorporated materials with their licenses and notices;
- records showing who created and controlled the relevant signing keys and when;
- any trademark, patent, copyright, or invention disclosures relevant to the project.

A qualified IP lawyer must review the chain of title and the applicable jurisdictions. This repository cannot prove that every contribution is legally owned by one person, and this checklist is not legal advice.

## Current project boundary

The present implementation is experimental. It includes deterministic transaction and block primitives, local block replay, and a single-host SQLite store. It does not yet implement distributed consensus, peer networking, validator selection, fork choice, production key custody, or a proven public-network protocol. No independent review, signed release, trusted timestamp, or legal chain-of-title conclusion is implied by the existence of this document.
