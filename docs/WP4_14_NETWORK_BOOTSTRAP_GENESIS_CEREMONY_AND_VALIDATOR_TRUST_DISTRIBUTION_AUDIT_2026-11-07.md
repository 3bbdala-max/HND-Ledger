# WP4.14 — Network Bootstrap, Genesis Ceremony and Validator Trust-Distribution Audit

**Date:** 2026-11-07  
**Branch:** `phase-0.2-planning`  
**Review type:** Static source, CI workflow and prior audit review; documentation-only.  
**Decision:** **NOT APPROVED** for production network bootstrap, public validator onboarding, production signing or public launch.  
**Change boundary:** This report adds documentation only. No source, tests, workflows, Genesis fixtures, keys, configuration or runtime behavior changed.

## 1. Executive determination

The repository demonstrates useful **disposable bootstrap mechanics**: CometBFT creates four temporary validator identities, a common Genesis document is assembled, that document is copied byte-for-byte to temporary homes, and a private four-validator smoke test reaches consensus and checks recovery/convergence.

That evidence is not a production Genesis ceremony or a trusted validator onboarding process.

The reviewed harness creates its validator keys and Genesis inside a temporary directory at test runtime. The HND manifest hash is calculated by the same test process and passed to each local HND application process as `--genesis-hash`. The Genesis file's SHA-256 is calculated and compared across the same temporary homes. This proves internal fixture consistency; it does **not** authenticate the origin or authorization of the initial validator roster.

No production-ready, signed, independently distributed network Genesis package was established in the reviewed artifacts. The repository's HND Genesis manifest describes account allocations and does not commit to the CometBFT validator roster. The separate CometBFT Genesis carries the validator keys and voting power, but the existing preflight does not bind it to an independently trusted signed release manifest.

The validator preflight helper parses the generated Genesis using CometBFT v0.40.0 types and asserts a validator count of four. It does not compare the exact roster, voting powers, consensus parameters or whole-file digest to an independently approved expected profile. The smoke test is valuable integration evidence, but its runtime-generated test identities are not a production bootstrap trust root.

**Interpretation:** this is a missing trust-distribution and operational-governance layer, not proof that the CometBFT Genesis parser or consensus implementation is broken.

## 2. Evidence inspected

### 2.1 Four-validator Genesis preflight

File: `scripts/cometbft_v040_four_validator_genesis_preflight.py`

Observed behavior:

- Creates four independent temporary CometBFT homes using the supplied binary's `init` command.
- Reads each generated `priv_validator_key.json` and derives validator records from the generated consensus public keys and addresses.
- Assigns fixture voting power `10` to each validator.
- Checks unique P2P node IDs and unique consensus validator addresses.
- Takes the first home’s generated CometBFT Genesis document, sets a test chain ID, initial height, validator records and HND app state, then writes the same Genesis bytes to all four homes.
- Computes a SHA-256 digest of the generated Genesis bytes and checks that each temporary home contains identical bytes.
- Calls `scripts/cometbft_v040_genesis_validate.go`, which parses the file using CometBFT Go types and checks that it contains four validators.
- Explicitly reports scope as Genesis/identity preflight only; it does not start nodes.

The HND manifest and its hash are also generated by this same preflight process. The fixture is disposable and test-scoped.

### 2.2 Four-validator running smoke

File: `scripts/cometbft_v040_four_validator_network_smoke.py`

Observed behavior:

- Generates fresh account keys, allocations and manifest for a test network.
- Computes `gh = genesis_manifest_hash(manifest)` inside the script.
- Creates four temporary CometBFT homes and four validator identities.
- Assembles a common Genesis containing the generated validator roster and HND application state.
- Copies the common Genesis bytes into all four homes.
- Starts each HND ABCI process with the same manifest path and the locally calculated `gh` supplied as `--genesis-hash`.
- Starts the four CometBFT processes and checks consensus-height/block-hash convergence, transaction replication and recovery.
- Uses temporary test keys and temporary process state; the test does not establish a persistent, independently authorized public validator roster.

The script's hash equality and convergence checks establish that the test participants used a consistent generated fixture. They do not show that the fixture was authorized by an independent protocol-owner trust root.

### 2.3 Genesis validation helper

File: `scripts/cometbft_v040_genesis_validate.go`

The helper calls `types.GenesisDocFromFile` and asserts `len(doc.Validators) == 4`. It prints chain ID, validator count and initial height.

It does not enforce an owner-approved chain ID, exact validator public-key roster, exact voting-power distribution, consensus parameter allowlist, expected CometBFT profile digest or expected complete Genesis digest.

### 2.4 HND manifest and startup boundary

Files:
- `hnd_v02/genesis.py`
- `hnd_v02/cometbft_v040_server.py)

The HND manifest hash is domain-separated and calculated over canonical HND manifest bytes. The validator smoke passes this hash through the CLI. The HND manifest is not the same artifact as CometBFT's full Genesis document: it does not contain CometBFT consensus public keys, validator addresses or voting power.

The HND server verifies the manifest against the supplied expected hash, but the trustworthiness of that expected hash depends on how it is provisioned. Supplying a digest computed by the same process from the same mutable manifest is not independent origin authentication.

### 2.5 CI workflow and previous governance evidence

File: `.github/workflows/hnd-v02-tests.yml`

The workflow executes the four-validator Genesis preflight and private four-validator network smoke, including remote-signer integration variants. Those are strong repeatable integration checks for the generated test fixture.

The workflow does not publish a signed production Genesis package, establish a validator-owner approval ceremony, verify a signed trust manifest, or attest that production nodes received the same independently approved roster.

## 4. Threat model and trust boundaries

A production bootstrap must protect against at least these cases:

1. **Genesis substitution:** an attacker or mistaken operator replaces the validator roster while retaining the same HND account manifest.
2. **Digest substitution:** an attacker replaces both a mutable configuration file and the digest stored beside it.
3. **Partial distribution:** some validators receive a newer roster or profile while others start from an older one.
4. **Unauthorized key enrollment:** a technically valid consensus public key is inserted without the required owner approval.
5. **Voting-power manipulation:** a roster preserves validator count while changing the weight distribution.
6. **Wrong-network replay:** a signed package for a different chain ID or Genesis identity is accepted.
7. **Stale package replay:** an old but once-valid bootstrap or membership package is reused after a later network change.
8. **Build/profile substitution:** the approved Genesis is launched with a different CometBFT binary or consensus profile.
9. **Compromised bootstrap operator:** one operator can unilaterally replace the roster or trust root.
10. **Signer/validator mismatch:** the node's active consensus key differs from the identity authorized in the approved roster.

Separate the authorities:

- HND application Genesis controls HND deterministic application configuration and allocations.
- CometBFT Genesis controls the initial CometBFT validator roster, voting power and consensus parameters.
- The network release/approval manifest binds the separate artifacts and their exact digests.
- A trust root provisioned independently authenticates the approval manifest.
- Each validator's deployment and signer controls prove that the local binary, profile and consensus key match the approved package.

A digest is a commitment to bytes; it does not prove who authorized those bytes.

## 5. Required production bootstrap package (proposal, not implemented)

A future bootstrap release should be a versioned, canonical, signed package with at least:

| Artifact | Required contents |
|---|---|
| Network identity manifest | Chain ID, identity/schema versions, network Genesis digest, activation/initial height and package sequence |
| HND application Genesis | Exact HND manifest and approved application-config identity |
| CometBFT Genesis | Exact validator roster, consensus public keys, voting power, consensus parameters and initial height |
| Validator-set artifact | Canonical ordered roster, derived addresses, public keys, power, owner approvals and roster digest |
| CometBFT profile artifact | Exact version-specific consensus/service profile and digest |
| Software identity | HND source commit/build identity, CometBFT source commit, build recipe, binary digest and dependency identities |
| Approval record | Required independent approver identities, signatures, roles, decision and reason |
| Activation record | Sequence, effective initial height, expiry, distribution status and supersession rules |
| Verification instructions | Canonicalization, signature algorithms, trust-root identifiers and exact verifier version |

No private keys, seed phrases, signer credentials or secret material may be included.

### Signature and trust-root rules

- The approval manifest must be signed by the protocol-defined independent authorization quorum.
- The verifier's trust roots must be provisioned out-of-band or protected by a separately authenticated installation process.
- Replacing the package and its local digest together must not make an unauthorized package acceptable.
- Signatures must cover the exact canonical package bytes or a rigorously defined domain-separated digest.
- Each signature must be bound to the chain ID, package type, schema version, sequence and intended activation context.
- The verifier must reject duplicate signers, unauthorized roles, insufficient distinct approvals, expired packages, unknown schema versions and replayed sequence numbers.
- Trust-root rotation must itself be authorized by the currently trusted policy or an explicitly documented recovery ceremony.
- Emergency recovery must not silently fall back to an unsigned Genesis or an empty validator roster.

The exact signer threshold and roles are protocol-owner governance decisions. This report does not invent or approve them.

## 6. Required bootstrap and distribution sequence

1. Freeze the HND application config, CometBFT profile, validator roster, consensus parameters and software build identities as separate artifacts.
2. Generate and validate the complete CometBFT Genesis using the exact pinned CometBFT version.
3. Independently recompute all artifact digests using a second implementation or independently reviewed toolchain.
4. Obtain the required independent approvals over the canonical package.
5. Publish the signed package and signature set through an authenticated distribution channel.
6. Provision each validator's trust roots independently of the package being verified.
7. On every validator, verify package signatures, chain ID, sequence, activation context, artifact digests, exact roster and local consensus key before starting CometBFT or enabling signing.
8. Exchange and compare per-node verification attestations; do not proceed if any required validator reports a mismatch.
9. Confirm that every node is configured for the same approved Genesis and consensus profile, while allowing only explicitly classified node-local settings to differ.
10. Start the network under a documented coordinated activation window and monitor height, block hash, app hash, validator participation and voting-power quorum.
11. Archive the package, signatures, independent verification output, approver record and activation evidence in immutable release records.
12. Any roster or profile change must create a new signed package sequence and activation plan; never mutate a live Genesis file in place.

A partial rollout must fail closed. A node must not automatically downgrade to a stale package to regain connectivity.

## 7. Acceptance-test matrix (proposed; not run)

| Test ID | Scenario | Required result |
|---|---|---|
| BOOT-T01 | Modify one validator public key but retain HND manifest hash | Whole-package verification rejects the altered roster. |
| BOOT-T02 | Modify one validator's voting power but retain validator count | Roster/profile digest mismatch is rejected. |
| BOOT-T03 | Replace one validator with another valid key, preserving four-member count | Exact trusted roster comparison rejects it. |
| BOOT-T04 | Change CometBFT consensus parameters while retaining HND app state | Approved CometBFT profile/Genesis digest check rejects it. |
| BOOT-T05 | Change chain ID in a signed package | Signature context/network identity verification rejects it. |
| BOOT-T06 | Replay a previously accepted package sequence | Reject as stale/replayed. |
| BOOT-T07 | Supply package with unknown schema version | Fail closed before listener startup or signing. |
| BOOT-T08 | Replace package and adjacent checksum together | Independent trust-root signature verification rejects unauthorized replacement. |
| BOOT-T09 | Remove one required approval signature | Reject for insufficient distinct authorized approvals. |
| BOOT-T10 | Duplicate one approver signature under multiple entries | Count the signer once; reject if quorum is not met. |
| BOOT-T11 | Use a valid signature from an unauthorized role/key | Reject. |
| BOOT-T12 | Expired or superseded package | Reject. |
| BOOT-T13 | Alter canonical bytes, key order or numeric lexical form | Reject non-canonical or signature-invalid encoding. |
| BOOT-T14 | Validator local consensus key differs from approved roster | Node must not start consensus or enable signing. |
| BOOT-T15 | One node receives a different Genesis package | Node fails closed and reports the precise digest mismatch. |
| BOOT-T16 | One node receives a different CometBFT binary digest | Node fails closed before consensus startup. |
| BOOT-T17 | One node uses an unapproved consensus profile | Node fails closed before network participation. |
| BOOT-T18 | Trust root is missing, malformed or substituted | Reject; no unsigned fallback. |
| BOOT-T19 | Trust-root rotation is signed only by the new, not currently trusted root | Reject unless an explicitly approved recovery rule authorizes it. |
| BOOT-T20 | Distribution is interrupted after only some validators acknowledge | Do not activate; retain prior approved package state. |
| BOOT-T21 | All validators verify the same package but report different local profile digests | Block activation and identify the divergent node. |
| BOOT-T22 | Valid package is copied to a wrong-network validator | Reject because chain ID and network identity do not match. |
| BOOT-T23 | Genesis file is valid CometBFT schema but has wrong owner-approved roster | Reject; schema validity alone is insufficient. |
| BOOT-T24 | Fresh test harness generates new temporary keys | Test remains clearly marked disposable; never publish as production enrollment evidence. |
| BOOT-T25 | Bootstrap completes | Archive signed package, approvals, independent verification and per-node attestations tied to exact commit and digests. |

These are proposed acceptance tests. They were not added to the repository test suite and were not executed.
